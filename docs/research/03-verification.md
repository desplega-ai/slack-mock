## Correction 3 (high)

The claim is directionally right but wrong on two points, both of which bite a mock server.

(1) The "exactly" list is incomplete: `reason` is also read. SocketModeClient.js:289 reads `event.reason` on the `disconnect` envelope (`Received "${event.type}" (${event.reason}) message - disconnecting.`). It is log-only, so it does not change behaviour, but the enumeration as written is false. Complete set of envelope fields read in onWebSocketMessage: `type` (283, 288, 289, 296, 301, 314, 326), `reason` (289), `envelope_id` (296, 298, 304, 316, 325), `payload` (302, 305, 306, 317, 327), `payload.event` (302, 306), `payload.event.type` (302), `retry_attempt` (307, 328), `retry_reason` (308, 329), `accepts_response_payload` (309, 318, 330). Nothing else in socket-mode or bolt touches the envelope.

(2) The crash-safety statement is too broad and hides the real trap. Only JSON.parse failures are safe (274-281). Frames that parse successfully but are not shaped as expected throw a synchronous TypeError inside the async `onWebSocketMessage`. That function is registered with `this.on('ws_message', this.onWebSocketMessage.bind(this))` (SocketModeClient.js:122) and eventemitter3 discards the returned promise, so the rejection is never handled. On Node 24 the default `--unhandled-rejections=throw` kills the process. Verified empirically against the installed libs with a real `ws` mock server:
  - `null` -> `TypeError: Cannot read properties of null (reading 'type')` at line 283, process exits with ERR_UNHANDLED_REJECTION.
  - `{"type":"events_api","envelope_id":"e1"}` (no payload) -> `Cannot read properties of undefined (reading 'event')` at line 302, process exits.
  - `{"type":"events_api","envelope_id":"e1","payload":{}}` (no payload.event) -> `Cannot read properties of undefined (reading 'type')` at line 302, process exits.
  - `not json` -> logged and dropped, survives (claim correct here).
  - `{"type":"events_api",...,"payload":{"event":{}}}` -> survives. `payload.event.type` may be absent; `this.emit(undefined, ...)` is legal in eventemitter3. So the hard requirement is `payload.event` being an object, not `payload.event.type` existing.

Mock-server rule that follows: every `events_api` envelope MUST carry `payload.event` as an object, and every text frame MUST parse to a non-null object. Otherwise the client under test dies rather than failing the assertion.

## Correction 4 (high)

The claim's STRUCTURE is confirmed, but one load-bearing quantifier is wrong, and three behaviours that matter for a mock server are missing.

CONFIRMED
1. Bolt subscribes to exactly one socket-mode emitter. `grep -rn "slack_event" node_modules/@slack/bolt/dist/` returns only SocketModeReceiver.js:133 (plus a comment in SocketModeFunctions.js:9). Only one `.on(` call exists in SocketModeReceiver.js.

3. hello and disconnect return before the emit: SocketModeClient.js:283-286 (hello) and :288-292 (disconnect). The cited range 283-292 is right.

REFUTED — "fires for every envelope that is not hello or disconnect"
Three further paths skip the `slack_event` emit at SocketModeClient.js:323:
a. Binary frames return at :265-268.
b. Non-JSON text frames return at :277-281.
c. MOST IMPORTANT for a mock: an `events_api` envelope without `payload.event` throws before the emit. Line 302 evaluates `this.emit(event.payload.event.type, ...)` eagerly inside the `if (event.type === 'events_api')` branch at :301. A frame like `{"type":"events_api","envelope_id":"x"}` raises a TypeError. `onWebSocketMessage` is an async handler bound at :123 (`this.on('ws_message', this.onWebSocketMessage.bind(this))`), so the throw becomes an unhandled promise rejection. Result: no `slack_event`, no Bolt call, no ack, and no visible error. A mock server sees a silent hang.
So the correct statement is: `slack_event` fires for every text frame that parses as JSON, is not `hello` or `disconnect`, and (when `type === "events_api"`) carries a `payload.event` object.

MISSING BEHAVIOURS THAT CHANGE MOCK-SERVER DESIGN (Lens B)
d. Ack ordering is not uniform. For Events API payloads Bolt acks BEFORE running listeners (App.js:646-652: `// Events API requests are acknowledged right away` then `await ack()`), except `function_executed`, which gets `listenerArgs.ack`. For commands, actions, options, views and shortcuts, `ack` is handed to the listener (App.js:643) and the mock must wait for listener code to call it.

Unlike HTTPReceiver, nothing auto-acks after 3s. The wrapper also silently swallows a second ack with a warn (SocketModeResponseAck.js:19-22), so a mock must not expect two ack frames.
f. Two paths produce NO ack at all. Classification reads the PAYLOAD keys (`body.event`, `body.command`, `body.actions`, `body.type`) at helpers.js:26-96, never the envelope `type`, so a mock must nest payloads exactly. By contrast, an authorize failure DOES get acked: App.js:457-470 sets `code = AuthorizationError` and the default error handler rejects (App.js:810-815), so the receiver catch runs and `defaultProcessEventErrorHandler` returns true (SocketModeFunctions.js:12-16), triggering `event.ack()` at SocketModeReceiver.js:152.

The mock must send `hello` first. `apps.connections.open` must also be mocked (:222-231), which needs `installerOptions.clientOptions.slackApiUrl` since SocketModeReceiver.js:27-31 forwards only `clientOptions`.

The reverse timer, `monitorPingFromSlack` (:180-186, 30000ms), arms only after the FIRST server ping (:95-101), so a mock that never pings does not trip it.

No trailing-slash issue exists on this path: the receiver's HTTP server and its `path-to-regexp` matching (SocketModeReceiver.js:104-121) only serve OAuth and custom routes, and are created only when an installer or customRoutes exist (:68).
